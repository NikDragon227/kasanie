# Спорт рядом — технический контур публичного поиска

## Задача

«Спорт рядом» — отдельный публичный модуль Kasanie для поиска любительских игр и совместных тренировок. Первый вертикальный сценарий — взрослый футбол: посетитель без регистрации находит событие по городу, району, дате и расстоянию, изучает карточку и может отметиться без создания аккаунта.

Модуль не является публичным представлением школьного кабинета. Детские профили, команды, тренировки, оценки и контакты родителей не попадают в публичный индекс и не используются публичными API.

## Границы доступа

| Действие | Гость | Авторизованный взрослый | Организатор события |
|---|---:|---:|---:|
| Поиск и просмотр карточек | Да | Да | Да |
| Просмотр площадки | Да | Да | Да |
| Запись | Да, по имени и контакту | Да | Да, на чужие события |
| Отмена записи | Да, по безопасной ссылке | Да | Да, на чужие события |
| Создание события | Нет | Да | Да |
| Редактирование/публикация/отмена | Нет | Нет | Только своего события |

Для игрока совершеннолетие определяется по дате рождения. Гость явно подтверждает возраст 18+ перед записью. Организатор сам выбирает, занимает ли он одно место в активности. Все мутации защищены CSRF-токеном; операции организатора дополнительно требуют cookie-аутентификацию.

Новый организатор регистрируется отдельно через `/register-organizer`: система требует 18 лет, имя для показа участникам, город, email и пароль. Ему назначается роль `Organizer` и создаётся `PublicOrganizerProfile`; профиль игрока при этом не создаётся. Email необходимо подтвердить до первого входа.

Титульная страница `/` разделена на два самостоятельных входа: публичный сценарий «Найти команду» ведёт в `/sports`, а «Начать тренироваться» — в `/join`. На `/join` доступны четыре варианта регистрации: игрок, родитель, тренер и организатор. Самостоятельно зарегистрированный тренер получает пустой кабинет и не видит игроков до назначения на команду школой. Роль из запроса проверяется по серверному allow-list: через публичную регистрацию нельзя получить административные роли.

Публичное чтение ограничивается по реальному IP после обработки forwarded headers, а запись и организаторские операции — по идентификатору авторизованного пользователя. Это защищает поиск от массового сканирования, а мутации — от частых повторов.

## API первой очереди

Публичные ручки:

- `GET /api/public/sports`;
- `GET /api/public/activities` — фильтры `sport`, `gameFormat`, `city`, `district`, `date`, `time`, `type`, `freeOnly`, `availableOnly`, `latitude`, `longitude`, `radiusKm` и сортировка `sort` (`recommended`, `distance`, `date`, `availability`, `price`);
- `GET /api/public/activities/{slug}`;
- `GET /api/public/venues`;
- `GET /api/public/venues/{slug}`.

Участие:

- `POST /api/public/activities/{id}/guest-join` — отметка без аккаунта;
- `GET /api/public/guest-participations/{token}` — просмотр своей гостевой записи по безопасной ссылке;
- `POST /api/public/guest-participations/{token}/cancel` — отмена своей гостевой записи;
- `POST /api/activities/{id}/join`;
- `POST /api/activities/{id}/leave`.

Регистрация организатора:

- `POST /api/auth/register-organizer`.

Регистрация участников платформы:

- `POST /api/auth/register` — игрок;
- `POST /api/auth/register-portal-user` — только родитель или тренер;
- `POST /api/auth/register-organizer` — организатор.

Организатор:

- `GET /api/organizer/activities/`;
- `POST /api/organizer/venues/` — новая публичная точка встречи по координатам, выбранным на карте;
- `POST /api/organizer/activities/`;
- `PUT /api/organizer/activities/{id}`;
- `POST /api/organizer/activities/{id}/publish`;
- `POST /api/organizer/activities/{id}/cancel`.
- `DELETE /api/organizer/activities/{id}` — архивирование своей активности;
- `GET /api/organizer/activities/{id}/participants` — закрытый список участников и гостевых контактов.

В публичном DTO нет email, телефона и Identity id организатора. Проверка владения выполняется сервером по `OrganizerId` текущего пользователя, а не по данным клиента.

## Данные и конкуренция

Основные сущности: `Sport`, `SportsVenue`, `PublicOrganizerProfile`, `PublicActivity`, `PublicActivityParticipant`. `PublicActivity.GameFormat` хранит состав одной стороны, а не общую вместимость: количество доступных мест организатор указывает отдельно. Для зарегистрированного участника действует уникальность `(PublicActivityId, UserId)`, для гостя — `(PublicActivityId, GuestContactHash)`. Запись выполняется в serializable-транзакции. Новые активности создаются без листа ожидания: после заполнения лимита запись закрывается. Контакт гостя доступен только владельцу события и не попадает в публичный DTO. После гостевой записи пользователю один раз выдаётся случайный токен управления; в базе хранится только его SHA-256-хеш. Ссылка позволяет просмотреть и отменить только эту запись, не раскрывая контакт участника.

Игровые форматы MVP:

- футбол: 5×5, 6×6, 7×7, 8×8, 9×9, 10×10, 11×11; число обозначает весь состав на поле и уже включает вратаря;
- баскетбол: 3×3, 5×5;
- волейбол: 2×2 (пляжный) или 6×6 (классический);
- хоккей: 3+1 (три полевых и вратарь) или 5+1 (пять полевых и вратарь).
- теннис и бадминтон: 1×1, 2×2;
- для бега и функциональных тренировок формат состава не применяется.

Поиск по радиусу использует предварительный bounding box в PostgreSQL и точный расчёт Haversine после выборки. Для масштабирования следующий шаг — PostGIS и spatial index.

## Feature flag и индексация

Модуль управляется параметром `PublicDiscovery:Enabled`. В Development он включён, в базовой production-конфигурации выключен до отдельного решения о публикации. Публичные страницы:

- `/` — развилка «Найти команду» / «Начать тренироваться»;
- `/join` — выбор роли для регистрации;
- `/sports` — каталог и поиск;
- `/activities/:slug` — индексируемая карточка события.
- `/guest/participations/:token` — неиндексируемое управление гостевой записью по секретной ссылке;
- `/register-organizer` — отдельная регистрация взрослого организатора.
- `/organizer/activities` — защищённый кабинет создания, публикации и отмены событий.

Текущая React SPA даёт рабочий пользовательский поток, но для полноценного SEO следующая фаза должна добавить SSR/пререндер, canonical URL, JSON-LD `SportsEvent`, sitemap и страницы вида «футбол в городе/районе».

Список событий и выбор точки встречи используют JavaScript API 2.1 Яндекс Карт. Для карты задайте `VITE_YANDEX_MAPS_API_KEY` до сборки frontend; без ключа поиск и карточки продолжают работать, а вместо карты показывается понятное состояние настройки. После записи и на странице управления доступны добавление события в календарь (`.ics`) и построение маршрута в Яндекс Картах.

## Продуктовые метрики поиска

В следующей итерации событийной аналитики фиксируем воронку без сохранения лишних персональных данных:

1. открытие поиска и применение фильтров;
2. просмотр карточки активности;
3. начало и успешное завершение гостевой либо авторизованной записи;
4. конверсия «поиск → карточка → участие» по городу, виду спорта и формату;
5. заполняемость события, время до первого участника и время до заполнения всех мест;
6. доля повторных организаторов и повторных посетителей;
7. отмены и неявки после появления соответствующего сценария.

Контакт гостя не должен использоваться как аналитический идентификатор. Для оценки повторных визитов нужен отдельный first-party идентификатор с ограниченным сроком жизни и описанием в политике обработки данных.

## Гипотезы удержания

- подписка на город, район, вид спорта и сохранённый набор фильтров;
- уведомление о новых подходящих событиях и напоминание перед началом;
- повторная запись в один клик по безопасной ссылке без обязательного профиля игрока;
- регулярные активности и кнопка организатора «Повторить событие»;
- личная история посещений и календарь предстоящих игр;
- знакомые организаторы и группы, которым можно доверять;
- рейтинг надёжности только после появления подтверждённых посещений и механизма споров.

Первая ставка на удержание — не баллы и искусственная геймификация, а экономия времени: человек быстрее узнаёт о следующей подходящей игре и возвращается в уже знакомую группу.

## Следующие фазы

1. Сохранённые наборы фильтров, повтор активности организатором и управление составом участников.
2. Уведомления о новых подходящих событиях и напоминания перед началом.
3. Площадки: предложения правок, модерация и верификация.
4. Сообщества: знакомые группы, жалобы, блокировки и модерация; чаты — только после проверки реальной необходимости.
5. SEO/география: SSR, PostGIS, посадочные страницы и поисковая аналитика.
6. Монетизация: платное поднятие карточек, подписка организатора и комиссия за платные события.

Перед публичным запуском нужны правила модерации, политика обработки геоданных, механизм жалоб, юридическая проверка и отдельная проверка возрастного шлюза.
