# Спорт рядом — технический контур публичного поиска

## Задача

«Спорт рядом» — отдельный публичный модуль Kasanie для поиска любительских игр и совместных тренировок. Первый вертикальный сценарий — взрослый футбол: посетитель без регистрации находит событие по городу, району, дате и расстоянию, изучает карточку и регистрируется только в момент записи.

Модуль не является публичным представлением школьного кабинета. Детские профили, команды, тренировки, оценки и контакты родителей не попадают в публичный индекс и не используются публичными API.

## Границы доступа

| Действие | Гость | Авторизованный взрослый | Организатор события |
|---|---:|---:|---:|
| Поиск и просмотр карточек | Да | Да | Да |
| Просмотр площадки | Да | Да | Да |
| Запись и отмена записи | Нет | Да | Да, на чужие события |
| Создание события | Нет | Да | Да |
| Редактирование/публикация/отмена | Нет | Нет | Только своего события |

Для игрока совершеннолетие определяется по дате рождения. Служебные взрослые роли проходят взрослый шлюз без доступа к детскому контуру. Организатор не занимает место участника собственного события. Все мутации требуют cookie-аутентификацию и CSRF-токен.

Новый организатор регистрируется отдельно через `/register-organizer`: система требует 18 лет, имя для показа участникам, город, email и пароль. Ему назначается роль `Organizer` и создаётся `PublicOrganizerProfile`; профиль игрока при этом не создаётся. Email необходимо подтвердить до первого входа.

Титульная страница `/` разделена на два самостоятельных входа: публичный сценарий «Найти команду» ведёт в `/sports`, а «Начать тренироваться» — в `/join`. На `/join` доступны четыре варианта регистрации: игрок, родитель, тренер и организатор. Самостоятельно зарегистрированный тренер получает пустой кабинет и не видит игроков до назначения на команду школой. Роль из запроса проверяется по серверному allow-list: через публичную регистрацию нельзя получить административные роли.

Публичное чтение ограничивается по реальному IP после обработки forwarded headers, а запись и организаторские операции — по идентификатору авторизованного пользователя. Это защищает поиск от массового сканирования, а мутации — от частых повторов.

## API первой очереди

Публичные ручки:

- `GET /api/public/sports`;
- `GET /api/public/activities` — фильтры `sport`, `city`, `district`, `date`, `time`, `type`, `freeOnly`, `availableOnly`, `latitude`, `longitude`, `radiusKm`;
- `GET /api/public/activities/{slug}`;
- `GET /api/public/venues`;
- `GET /api/public/venues/{slug}`.

Участие:

- `POST /api/activities/{id}/join`;
- `POST /api/activities/{id}/leave`.

Регистрация организатора:

- `POST /api/auth/register-organizer`.

Регистрация участников платформы:

- `POST /api/auth/register` — игрок;
- `POST /api/auth/register-portal-user` — только родитель или тренер;
- `POST /api/auth/register-organizer` — организатор.

Организатор:

- `GET /api/organizer/activities/`;
- `POST /api/organizer/venues/` — новая публичная точка встречи по координатам, выбранным на карте;
- `POST /api/organizer/activities/`;
- `PUT /api/organizer/activities/{id}`;
- `POST /api/organizer/activities/{id}/publish`;
- `POST /api/organizer/activities/{id}/cancel`.

В публичном DTO нет email, телефона и Identity id организатора. Проверка владения выполняется сервером по `OrganizerId` текущего пользователя, а не по данным клиента.

## Данные и конкуренция

Основные сущности: `Sport`, `SportsVenue`, `PublicOrganizerProfile`, `PublicActivity`, `PublicActivityParticipant`. Для участника действует уникальность `(PublicActivityId, UserId)`. Запись выполняется в serializable-транзакции; при заполнении основной квоты используется лист ожидания. После освобождения подтверждённого места первый ожидающий автоматически переводится в подтверждённые.

Поиск по радиусу использует предварительный bounding box в PostgreSQL и точный расчёт Haversine после выборки. Для масштабирования следующий шаг — PostGIS и spatial index.

## Feature flag и индексация

Модуль управляется параметром `PublicDiscovery:Enabled`. В Development он включён, в базовой production-конфигурации выключен до отдельного решения о публикации. Публичные страницы:

- `/` — развилка «Найти команду» / «Начать тренироваться»;
- `/join` — выбор роли для регистрации;
- `/sports` — каталог и поиск;
- `/activities/:slug` — индексируемая карточка события.
- `/register-organizer` — отдельная регистрация взрослого организатора.
- `/organizer/activities` — защищённый кабинет создания, публикации и отмены событий.

Текущая React SPA даёт рабочий пользовательский поток, но для полноценного SEO следующая фаза должна добавить SSR/пререндер, canonical URL, JSON-LD `SportsEvent`, sitemap и страницы вида «футбол в городе/районе».

Список событий и выбор точки встречи используют JavaScript API 2.1 Яндекс Карт. Для карты задайте `VITE_YANDEX_MAPS_API_KEY` до сборки frontend; без ключа поиск и карточки продолжают работать, а вместо карты показывается понятное состояние настройки.

## Следующие фазы

1. Расширение кабинета организатора: редактирование, список участников, уведомления и повторяющиеся серии.
2. Площадки: предложения правок, модерация и верификация.
3. Сообщества: лента, комментарии, личные сообщения, жалобы, блокировки и модерация.
4. SEO/география: SSR, PostGIS, региональные посадочные страницы и поисковая аналитика.
5. Монетизация: платное поднятие карточек, подписка организатора и комиссия за платные события.

Перед публичным запуском нужны правила модерации, политика обработки геоданных, механизм жалоб, юридическая проверка и отдельная проверка возрастного шлюза.
